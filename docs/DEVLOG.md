# 开发日志

NewStart NZ — 奥克兰租金 × 治安 suburb 选区工具。

这份日志记录踩过的坑和当时为什么那么决定，按阶段而不是按天。真正花时间的从来不是画地图，
是让两套政府数据在地理上对得上。

---

## 阶段一：接上 MBIE API

新西兰商业创新就业部（MBIE）的 Market Rent API v2 提供官方租金统计。

```
https://api.business.govt.nz/gateway/tenancy-services/market-rent/v2
鉴权：Ocp-Apim-Subscription-Key 请求头
```

摸清楚的几件事：

- `area-definition` 有多个粒度，最细的是 `statistical-area-unit-2019`（SAU，统计区单元）。
  territorial-authority 粒度太粗，整个奥克兰才几行，没法做 suburb 级别的对比。
- SAU 粒度 + 12 个月滚动窗口是能拿到的最细数据，但请求慢——8,843 行、1.7MB，约 120 秒。
  小请求（TA 粒度、单月）是秒级的。
- 当时最新可用周期是 `period-ending=2025-12&num-months=12`。试过 `2026-03`，SAU 粒度直接返回 500，
  推测是 Bond Hub 迁移还没完成，粗粒度反而是通的。（这个窗口后来变了，见阶段六。）

字段里 `med`（中位数）、`mean`（平均数）、`lq`/`uq`（四分位）、`nCurr`（当前有效保证金数）都有用。
中途试过把展示值从 `med` 换成 `mean`，跑完看了下——Auckland Central 两居室 $705 → $719，
平均数被高端房源拉高，对「我能租到什么」这个问题反而失真，换回了 `med`。

## 阶段二：核心障碍——两套数据不共享地图

这是整个项目最花时间的部分，也是它真正的技术内容。

租金和治安数据都是公开且权威的，但**没人能把它们放一起看**，因为地理边界完全不同：

| 数据源 | 分区方式 | 例子 |
|---|---|---|
| MBIE 租金 | 统计区单元（SAU） | `Mount Eden East`、`Beach Haven West`、`Saint Heliers North` |
| NZ Police 治安 | 警方自己的分区 | `Maungawhau`、`Lynfield North`、`Beachhaven South` |
| 普通人说的 | suburb 名 | `Mt Eden`、`Beachhaven`、`St Heliers` |

三套命名互不重合。解决办法是建一层调和映射：两个 CSV，把 556 个租金源区域和 416 个警方源区域
逐个折叠到一组共用的 master suburb 上。

### 教训：地名不能当主键

这个坑反复踩了**四次**，每次表现都一样——某个 suburb 数据莫名其妙是空的：

| 次序 | suburb | 真实原因 |
|---|---|---|
| 1 | Mt Eden / Mt Albert / Mt Roskill | 源数据写 `Mount`，匹配写 `Mt`，模糊匹配失败 |
| 2 | Beachhaven | 源数据是 `Beach Haven`（两个词） |
| 3 | St Heliers | 源数据是 `Saint Heliers`（全拼） |
| 4 | Beachlands / Flat Bush | 源数据用完全不同的地名（`Maraetai`、`Sunkist Bay`、`Ormiston`）|

前三次都是同一类拼写变体问题。第四次不是拼写而是地名本身不同——Ormiston 是 Flat Bush 区域内的
一个中心，源数据只认 Ormiston。

**没有靠模糊匹配解决，全部改成显式映射表。** 模糊匹配在这个场景下是危险的：它会静默地漏掉，
而不是报错，你只有肉眼看到某个格子空了才会发现。映射表是穷举的，每一条都标 `mapped` 或
`not mapped` 并写原因，漏掉就一眼能看出来。

第一版映射做完之后，很多数字明显变了（Auckland Central 独立屋两居 $765 → $705，
公寓一居 $548 → $484）——说明之前的模糊匹配一直在拿错的区域算平均。

## 阶段三：交互结构

### 「All」放错了地方

最初 1B/2B/3B/4B 和 House/Apartment 两组按钮都带 All。这是错的：
**卧室数的「全部」没有意义**——把一居和四居的租金平均起来不对应任何真实的租房决策。
而房型的「全部」是有意义的：「两居室，独立屋或公寓都行，多少钱」是个正常问题。

改成 All 只出现在房型那一组，卧室数必须选一个具体值。

### 缺失数据显式暴露

有几个 suburb 在某个筛选组合下没有数据。填零或填均值都会骗人——填零会让它在「最便宜」
排行榜里排第一。统一显示 `No data`，并在推荐表里明确写出被排除了几个。

## 阶段四：可视化重构（四象限）

从「租金一张图、治安一张图」改成把两个维度同时呈现。

以**当前筛选下**的租金中位数和犯罪中位数为分界，把 suburb 分四类：

```
低租金 + 高安全 → Best value       #1D9E75
高租金 + 高安全 → Premium          #5B8DEF
低租金 + 低安全 → Budget           #EF9F27
高租金 + 低安全 → Not recommended  #E24B4A
```

关键点：**中位数随筛选重算**。切到四居室时租金中位数会整体上移，象限归属也跟着变——
象限描述的是「在这个价位段里的相对位置」，不是绝对标签。

配套加了并排散点图（X 轴租金、Y 轴对数犯罪数取反、点大小是保证金数量）和底部全宽推荐表。
散点图和地图双向联动：任意一边 hover 高亮另一边，点击同时选中并把地图 zoom 过去。

散点图用手写 SVG，没上图表库——项目一直是零构建的单文件 HTML，为了一张散点图引入
依赖不值得，而且 SVG 直接生成也就 80 行。

## 阶段六：重探 API，发现漏了一半房源

隔了一段时间重新探测 API，三个发现：

**可用时间窗口是移动的。** 之前 `2026-03` 在 SAU 粒度返回 500，现在通了；反而是 `2025-06` 失效了。数据更新到 `2026-06`（覆盖 2025-07~2026-06）。不过比对了 13 个 ward 的两居独立屋，半年只动了 −0.7%，所以更新数据不改变任何结论。

**`ward-2019` 是 API 原生粒度。** 直接返回 13 个真实 Auckland ward。这解释了之前 spec 里那份 ward 表为什么全对不上——那是 **local board（21 个）**的名字，不是 ward（13 个），两套体系边界不同。

**`dwell` 有 5 个取值，我们只用了 2 个。** 这是最严重的一条：

| dwell | 1br 中位 | 有效保证金 | 当时状态 |
|---|---|---|---|
| Boarding House | $350 | 864 | ✗ 缺失 |
| Room | $370 | 2,565 | ✗ 缺失 |
| Flat | $430 | 18,018 | ✗ 缺失 |
| Apartment | $488 | 22,413 | ✓ |
| House | $650 | 123,939 | ✓ |

这个产品是给留学生和新移民做的，而他们租得最多的恰恰是 Flat（合租整套）和 Room（单间）。一间 room $370/周，比我们当时展示的最便宜选项还低一大截。**等于把目标用户最相关的三类房源全过滤掉了。**

补上之后「All」的定义也得改——把按房间计价的 $370 和整套房的 $600 平均成一个数没有意义。现在 All 只含整租三类（House/Apartment/Flat），选 Room / Boarding House 会自动锁定 1 bed。这和阶段三「All 放错地方」是同一个判断。

## 阶段七：三级粒度与下钻

粒度从两档扩到三档，并且点击即下钻：

```
Regions(6) ──点 East──▶ Suburbs(62) ──点 Howick──▶ Raw(源区域)
```

下钻会带一个 `scope`，**图表、地图、KPI 三者一起收窄**——钻进 East 之后中位租金显示的是 East 的值，不是全奥克兰的。

最细那档是各数据源**原始的边界**（租金 548 个 SAU、治安 405 个警方分区）。地图在这一档停在 suburb 层，因为这些源区域**只有名字没有坐标**，画不出来；界面明说了这点而不是让用户自己纳闷。

调这一档时挖出三个只有真跑起来才会暴露的 bug：

1. **地图被撑到 3589px。** flex 项默认 `min-height: auto`，超高的 bar chart SVG 把整行撑开，地图跟着变形。加 `min-height: 0` 才把滚动约束回图表面板内。
2. **187 根柱子被压进一屏。** 样式表的 `#scatter { height: 100% }` 覆盖了 SVG 的 height 属性，viewBox 把内容整体缩放。bar 模式改成显式设置像素高度。
3. **地图用错基准分象限。** 切粒度后只重建了标记，没重算中位数——结果拿 ward 的中位数（$590）给 suburb 上色。改成走 `refresh()`。

## 阶段八：文档描述了不存在的代码

写完架构文档之后才发现一个尴尬的事实：**文档里描述的那套 Python 管线根本不在仓库里。**

`ARCHITECTURE.md` 写着「a Python aggregation runs offline」还详述了聚合规则，但抓 API、跑映射、算聚合的脚本我全是在临时目录里跑的，一个都没提交。仓库里只有最早那个探测 API 的 `test_mbie_api.py`。

结果是 `data/suburbs.json` 成了**没有源码的产物**——源数据一更新就没法重新生成。

补了三个脚本（`fetch_rent.py` / `build_dataset.py` / `inline_data.py`），**验证方式是往返比对**：重新生成的 JSON 与已提交版本逐字节一致，注入后 HTML 无改动。这证明脚本确实是当时那套逻辑，不是事后补的近似品。

往返比对还顺带抓到一个偏差：`auckland_map.html` 一直停在 2025-12 的旧数据，刷新时只重新注入了 prototype 把它漏了。**这正是没有管线会出的问题。**

## 已知问题

按重要性排序。

### 1. 犯罪数是绝对值，不是人均

Auckland Central 4,914 起、Glendowie 25 起，但两者人口和人流量差了几个数量级。
现在的算法会**系统性地惩罚市中心和大型 suburb**，Auckland Central 永远落在
「Not recommended」象限。

要修需要引入各 suburb 人口数做标准化。这是目前最影响结论可信度的问题。

### 2. CBD 被标成「最安全」

拆出 CBD 之后界面显示 `SAFEST: CBD, 4,914 incidents`，而 Auckland Central 在 61 个有数据的
suburb 里犯罪数排**第 2 高**。

原因是犯罪数**求和**，而各区 suburb 数量差很远：

| 区 | suburb 数 | 犯罪总数 | 平均每 suburb |
|---|---|---|---|
| CBD | 1 | 4,914 | **4,914** |
| Central | 11 | 6,758 | 614 |
| East | 16 | 7,672 | 480 |
| South | 12 | 18,864 | 1,572 |

CBD 只装 1 个 suburb，总数自然最小。这不是拆 CBD 引入的新 bug——East(16) 和 North(9) 本来
就不可比，CBD=1 只是把它放大到一眼可见。**这是第 1 条那个问题的直接后果。**

### 3. 社会住房拉低中位数

最便宜的源区域是 Glen Innes East-Wai O Taiki Bay，2 居室 **$194/周**，`nCurr` 有 219、
`lq` 低到 $127。查了不是异常值——是 **Kāinga Ora 社会住房**，income-related rent 按收入 25% 计。

范围不广（只有 4 个源区域符合特征，其中 3 个还在覆盖范围外），但 **Glen Innes 确实被拉低了**：
聚合后 2 居室独立屋 $404，是 $194 和 $615 的平均，私人市场租不到这个价。

没改，因为那是真实的官方数据。要处理得能区分社会住房与私人房源，MBIE 数据里没有这个字段。

### 4. 圆点坐标是手打的

`suburbs.json` 里的 lat/lng **没有任何权威来源**，是最早脚本里一个硬编码字典，按大致印象填的。
证据是精度不一致：3 个 suburb 两位小数、58 个三位、1 个四位。

看起来都对——每个点都落在合理位置——但**是目测级精度，不是 centroid**。在一个号称做地理数据
调和的项目里，这是个不协调的短板。

修法：LINZ 的 NZ Suburbs and Localities 数据集有官方边界，算 centroid 就是真坐标。修完还能
顺带解锁 choropleth 色块和地址搜索的 point-in-polygon。

### 5. 稀疏组合仍会产生离谱数字

「4 bed+ · Apartment」是最明显的例子——Auckland Central 报 $302/周、15 份保证金。四居室公寓
不是这个价，看着像按房间分租的房源被归错了类。

没有设样本量下限，tooltip 会显示 `nCurr` 让读者自己判断，但低样本目前没有视觉标记。

### 6. 边界只是近似对齐

租金的 SAU 和警方分区形状本来就不一样，折叠到同一个 suburb 上必然有误差。
suburb 级数字是**指示性的，不是精确值**。

### 7. 覆盖率

62 个 suburb 涵盖 55,970 起案件，占全奥克兰 79,812 起的 70%。
剩下 30% 分布在外围区域（Papakura、Pukekohe、Waiheke 等），不在覆盖范围内。

### 8. Flat Bush 没有治安数据

租金已经通过 Ormiston 补上了，但警方数据里 Ormiston 被归到了 Botany。
没有改——把 Ormiston 的案件从 Botany 挪走会让 Botany 的数字失真，而且 Flat Bush 只拿到
一个警方分区的话本身也是低估，反而会让它错误地显示成「很安全」。宁可留空。

## 如果继续做

按投入产出排序：

1. **引入人口数据做人均犯罪率** — 唯一能实质提升结论可信度的改动，同时解决 CBD 那个假结论
2. **LINZ 边界数据** — 一次解决三件事：真 centroid 换掉手打坐标、圆点换成 choropleth 色块、
   解锁地址搜索的 point-in-polygon
3. **样本量阈值提示** — nCurr 太低的格子标注「数据稀疏」，而不是当作可靠值展示
4. **suburb 详情页** — tooltip 里的「View suburb details →」还没有落地页
5. **时间序列** — MBIE 有历史数据，可以做租金走势
